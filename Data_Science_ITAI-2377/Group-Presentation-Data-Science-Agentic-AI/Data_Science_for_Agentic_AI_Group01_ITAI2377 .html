What Is Agentic AI?

ITAI 2377 · Data Science  |  Prof. Sitaram Ayyagari  |  Group 0102 / 13
  • A regular AI chatbot answers one question and then stops. You ask, it answers, conversation over. That's generative AI.
  • An agentic AI is different — it is given a goal, and it keeps working on that goal by itself until the goal is finished.
  • The agent can decide to search the web, run code, query a database, send an email, or call another tool — then look at the result and decide what to do next.
  • In short: Agent = LLM brain + tools + memory + a loop. The model itself is the one making decisions, not the user.
  • Examples already in use today: coding assistants that fix their own bugs, research agents that write reports with citations, customer-support agents that actually take action instead of just talking.
Why the class cares: building these systems is not about a single model call. It is about the data that flows in, out, and between every step.

Generative vs. Agentic: What Changed

ITAI 2377 · Data Science  |  Prof. Sitaram Ayyagari  |  Group 0103 / 13
Dimension Generative AI Agentic AI
Input A prompt from the user A goal plus an environment to work in
Steps taken One (prompt → answer) Many — the agent loops until done
Memory None between calls Short-term + long-term, persistent
Tools Optional Core capability — the agent calls APIs, databases, code
Who is in charge The user directs every step The model directs itself toward the goal
Main failure mode Hallucinating an answer Looping forever, drifting off-goal, spending money
The shift from generative to agentic is what makes AI actually useful for real work — but it also makes the data problem much bigger.

The four data surfaces inside every agent

  • Knowledge data — documents, vectors, knowledge graphs the agent reads from
  • Tool I/O — every API call, every return value, every error
  • Memory state — short-term scratchpads and long-term stored facts
  • Trajectories — the full step-by-step trace of a run, used for evaluation

Why classical data science skills transfer

  • ETL pipelines → ingest, chunk, and embed documents for retrieval
  • Feature engineering → context construction and prompt design
  • Model evaluation → scoring trajectories and LLM-as-judge methods
  • Monitoring → token cost, latency, tool failure rate, data drift

Anatomy of an Agent: The Four Parts

ITAI 2377 · Data Science  |  Prof. Sitaram Ayyagari  |  Group 0105 / 13
01 · BRAIN

LLM

The reasoning engine. Looks at the goal plus the current context and decides what to do next.

GPT-4, Claude, Llama 3.3, Gemini

02 · HANDS

Tools

Functions the agent can call: web search, SQL, email, code execution, any API.

JSON schema → function call

03 · MEMORY

Storage

Short-term for the current task, long-term vector database for past runs and stable facts.

Pinecone, Chroma, Weaviate

04 · CONTROL

Orchestration

The loop that ties it together — planner, router, retry logic, stopping condition.

LangGraph, CrewAI, AutoGen

The LLM comes pre-trained by someone else. Tools, memory, and orchestration are all built from data you own. That is where data science sits — three of the four building blocks belong to us, not to the model provider.

The Loop: Perceive → Reason → Act → Reflect

ITAI 2377 · Data Science  |  Prof. Sitaram Ayyagari  |  Group 0106 / 13
01 / PERCEIVE

Observe

Read the goal, pull relevant memory, check the result of the previous tool call.

02 / REASON

Plan

The LLM decides which tool to use next, with what arguments — or whether the goal is done.

04 / REFLECT

Evaluate

Did it work? Update memory, score the step, decide whether to continue or stop.

03 / ACT

Execute

Call the tool. Capture result, errors, latency, cost. This is the data event.

What gets logged at every step

  • Inputs: goal, retrieved context, prior steps
  • Reasoning: the LLM's chain-of-thought
  • Tool call: function name, JSON arguments, timestamp
  • Result: return value, error, tokens used, latency in ms
  • Reflection: success flag, score, next-step decision
Every loop produces a trajectory — a structured record of one full run. Trajectories are our training data, our evaluation set, and our debugging tool, all at once.

The Data Pipeline Behind a Working Agent

ITAI 2377 · Data Science  |  Prof. Sitaram Ayyagari  |  Group 0107 / 13
STEP 01

Ingest

Pull raw sources: PDFs, APIs, databases, web pages, internal documents.

STEP 02

Chunk & Clean

Split into 200–800 token chunks. Strip noise. Keep structure like headings and tables.

STEP 03

Embed

Turn each chunk into a vector using an embedding model like text-embedding-3 or BGE.

STEP 04

Index

Store in a vector database. Add metadata filters: date, source, permissions.

STEP 05

Retrieve

At runtime, fetch the top-k chunks for the agent's current step. Re-rank if needed.

Where most agents fail

  • Chunks too big — the model loses focus in long context
  • Chunks too small — context fragments lose meaning
  • Bad metadata — agent retrieves the wrong tenant's data
  • Stale index — knowledge drifts from reality

The data scientist's job

  • Tune chunk size and overlap for your corpus
  • Build eval sets of (question → expected chunk) pairs
  • Measure retrieval recall@k before blaming the LLM
  • Schedule re-indexing as sources change

Memory: What Makes an Agent Different

ITAI 2377 · Data Science  |  Prof. Sitaram Ayyagari  |  Group 0108 / 13

Short-term

The current task's scratchpad, held inside the model's context window.

  • The goal and the plan
  • Tool calls made so far
  • Intermediate results

Cleared when task ends

Long-term episodic

Past trajectories the agent can search to learn from prior runs.

  • "How did I solve this before?"
  • Stored as embeddings plus metadata
  • Retrieved by similarity

Persists across sessions

Long-term semantic

Stable facts about the world, the user, and the domain.

  • User preferences
  • Company knowledge base
  • Tool documentation

Curated and versioned

The data problem nobody warns you about: memory grows without limit. Without summarization, deduplication, and a forgetting policy, retrieval gets slower, costlier, and less accurate over time. Memory management is the new database administration.

Evaluation: Three Layers, Four Metrics

ITAI 2377 · Data Science  |  Prof. Sitaram Ayyagari  |  Group 0109 / 13

Three layers of evaluation

LayerWhat it measures
Step-levelWas each tool call correct? Right args?
TrajectoryDid the full sequence reach the goal?
OutcomeDid the user or business actually benefit?

Methods

  • Golden trajectories — hand-labeled "correct" runs as a benchmark
  • LLM-as-judge — a stronger model scores the agent's output
  • Programmatic checks — unit tests on tool outputs
  • Human-in-the-loop — sample 5% of runs for manual review

Metrics that actually matter

Task Success Rate

The percentage of runs that reach the goal. Your headline number.

Steps to Solution

Fewer is better — this is your plan-quality signal.

Cost per Task

Tokens × price. Agents loop, so costs can spiral fast.

Tool Error Rate

Percentage of tool calls that fail. Often the real root cause.

Accuracy alone is a lie. Always track cost and latency next to success rate.

Case Study 1 Deep Dive: GitHub Copilot

ITAI 2377 · Data Science  |  Prof. Sitaram Ayyagari  |  Group 0111 / 14

GitHub's Copilot Agent is a coding agent built into the developer's editor. Instead of just suggesting the next line of code, the agent is given a task — "fix this bug" or "add this feature" — and it works on it step by step.

To do that, the agent uses a full data pipeline. It indexes the whole codebase as embeddings so it can retrieve the right files. It calls tools — it can run tests, search the repo, edit files, and open a pull request. It remembers previous attempts in the same task so it does not repeat mistakes.

Every step is logged as a trajectory. GitHub uses those trajectories both to debug failures and to fine-tune future versions of the agent.

Data science layers: code embeddings · tool-call logs · test-run results · human feedback on pull requests.

55%
Faster completion of routine coding tasks reported by GitHub in their 2023 productivity study
1.3M+
Paid Copilot subscribers by late 2024 — a mainstream, production agent system

Mode launched publicly in 2025 — shifts Copilot from autocomplete to true task execution

Case Study 2 Deep Dive: Klarna

ITAI 2377 · Data Science  |  Prof. Sitaram Ayyagari  |  Group 0112 / 14

Klarna is a global payments and shopping company with tens of millions of customers. In 2024 they replaced a large part of their customer-support operation with an AI agent built on OpenAI's models.

The agent is a real agentic system — it does not just answer questions. It retrieves the customer's order history from internal databases, calls tools to issue refunds, update addresses, and check shipments, and escalates to a human when confidence is low.

The data pipeline behind it matters more than the model: policy documents, product knowledge, and past conversations all had to be cleaned, embedded, indexed, and continuously updated. The agent's trajectories are reviewed daily for quality.

Data science layers: conversation memory · order database tools · policy retrieval · satisfaction scoring · human review of trajectories.

Key Takeaways

ITAI 2377 · Data Science  |  Prof. Sitaram Ayyagari  |  Group 0113 / 14
  • An agent is not a smarter chatbot. It is an LLM + tools + memory + a loop, and three of those four are data science problems.
  • The real work is not the model call. It is the pipeline behind it — ingest, chunk, embed, index, retrieve.
  • Every run produces a trajectory. Without trajectories, you cannot debug, evaluate, or improve the agent.
  • Evaluate at three layers: step, trajectory, and outcome. Always track cost and latency alongside accuracy.
  • Memory grows without bound. Plan for forgetting before you plan for remembering.
  • Real production systems — Copilot, Klarna, and many others — prove agentic AI is no longer research. The differentiator is the quality of the data plumbing behind it.

Remember

Agent = LLM + tools + memory + loop. Data science owns 3 of those 4.

Measure

Every step is a trajectory. Without traces, nothing improves.

Beware

Cost and memory grow fast. Build budgets and forgetting from day one.
